# 불변식과 실패 시나리오

> WBS 1.1 · 이슈 #2
> **이 문서는 직접 작성한다.** Claude는 뼈대와 질문만 만들었다. 다 쓰면 Claude에게 설계 반박을 받고, 반박을 반영한 뒤 PR을 올린다.

하루거래소의 모든 설계는 아래 다섯 가지 불변식을 지키기 위해 존재한다. 이 문서는 각 불변식이 **정확히 무엇을 뜻하는지**, **어떻게 깨질 수 있는지**, **무엇이 그것을 막는지**, **어떻게 깨뜨려 볼 것인지**를 정한다. 1단계 이후 속성 기반 테스트, 장애 실험, ADR이 이 문서를 근거로 삼는다.

## 작성 방법

불변식마다 아래 다섯 칸을 채운다.

| 칸 | 쓸 내용 |
| --- | --- |
| 정의 | 불변식을 검사할 수 있는 식이나 조건으로 다시 쓴다. "음수가 될 수 없다"를 어떤 값의 어떤 조건으로 확인하는지까지 |
| 책임 계층 | 엔진, API, 체결 반영 소비자, DB 제약, 배치 중 어디가 지키는가. 여러 곳이면 각자 무엇을 맡는지 |
| 검사 시점 | 언제 참이어야 하는가. 명령 하나 처리 후, 트랜잭션 커밋 후, 장 마감 후 등 |
| 실패 시나리오 | 이 불변식이 깨지는 구체적인 순서. "A가 일어나고, B가 일어나는 사이에 C가 일어나면" 형태로 |
| 막는 장치 / 테스트 | 시나리오마다 무엇이 막는지, 그리고 그걸 어떻게 테스트로 깨뜨려 볼지 |

실패 시나리오는 불변식마다 **최소 세 개**를 쓴다. 정상 흐름의 버그, 동시성, 장애(프로세스 종료·재시도·중복 전달) 중 서로 다른 종류에서 하나씩 나오면 좋다.
