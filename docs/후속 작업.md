## 백엔드 CI 경로 필터 방식 변경

**처리 시점:** `main` 브랜치 보호에서 `backend` 워크플로를 필수 검사(required status check)로 지정할 때. 지정하는 작업과 같은 PR에서 바꾼다.

**현재 상태.** `.github/workflows/backend.yml`은 워크플로 레벨의 `paths-ignore`로 프론트엔드와 문서 변경을 건너뛴다.

```yaml
pull_request:
  paths-ignore:
    - 'frontend/**'
    - '.github/workflows/frontend.yml'
    - 'docs/**'
    - '**/*.md'
```

**문제.** 경로 필터로 트리거되지 않은 워크플로는 "건너뜀"으로 보고되지 않고 **아무 결과도 보고하지 않는다.** GitHub는 필수 검사의 결과를 계속 기다리므로, 프론트엔드나 문서만 바꾼 PR이 `Expected — Waiting for status to be reported` 상태로 남아 머지할 수 없게 된다.

**바꾸는 방법.** 워크플로는 항상 실행하고, 실행 안에서 변경 경로를 판단해 건너뛴다.

1. 워크플로 레벨의 `paths-ignore`를 지운다.
2. 첫 job에서 변경 경로를 확인한다 (예: `dorny/paths-filter`).
3. 백엔드 변경이 없으면 빌드 job을 `if:`로 건너뛴다. job 단위로 건너뛴 경우 GitHub는 필수 검사를 통과한 것으로 본다.
4. 또는 모든 job의 결과를 모으는 집계 job(예: `backend-ok`)을 하나 두고, 그 job만 필수 검사로 지정한다.

`frontend.yml`도 워크플로 레벨의 `paths`로 `frontend/**`만 받는다. `frontend`를 필수 검사로 지정하면 백엔드만 바꾼 PR에서 같은 문제가 생기므로 함께 바꾼다.

## Modulith `event_publication` 테이블 마이그레이션

**처리 시점:** 2단계(주문·잔고·원장) Flyway 스키마 작업 때.

`spring-modulith-starter-jpa`가 쓰는 이벤트 발행 기록 테이블(`event_publication`)의 Flyway 마이그레이션이 아직 없다. 그래서 테스트가 끝날 때 테이블이 없다는 경고가 나온다. 지금은 무시해도 되지만, 모듈 간 이벤트를 쓰기 시작하면 실제로 실패한다.

## Spring Modulith 사용 범위 ADR

**처리 시점:** WBS 0.6.

0.2에서 정한 내용을 ADR-0001("Spring Modulith 사용 범위")로 기록한다.

- `2.2.0` GA 사용
- 모듈 경계 검증·문서화, 이벤트 발행 기록(`starter-jpa`)은 유지
- `events-kafka`는 제거. at-least-once 재발행이 종목별 순서를 보장하지 않으므로 `order.commands`는 `(symbol, seq)` 순서로 발행하는 직접 구현 Outbox가 담당

## 장애 복구 화면의 해시 검증 실제 연동

**처리 시점:** F.13 백엔드 연동 (3단계 Kafka·복구가 끝난 뒤).

장애 복구 화면(F.8)은 목 데이터로 동작한다. 목 데이터는 시장을 멈춘 채 해시를 다시 계산하므로 복구 전후 해시가 **항상 일치한다.** 화면 흐름과 표시만 검증된 상태이므로, 연동할 때 실제 엔진의 스냅샷·재생·해시 결과를 받아 판정하도록 바꾼다. 시세 출처는 `frontend/src/data/market.ts`의 `marketSource` 한 줄을 실제 구현으로 바꾸는 구조다.
